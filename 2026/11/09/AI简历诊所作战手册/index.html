AI简历诊所作战手册：五周从零到初赛提交的完整路线

发表于2026-11-09|更新于2026-11-09|竞赛
|总字数:3.1k|阅读时长:10分钟|浏览量:

配套阅读：本站《华为ICT大赛创新赛参赛建议：C++竞赛生队伍怎么选赛道、做什么、怎么分工》讲清了为什么选赛题1、为什么做奖励模型项目、三人怎么分工。本文是它的落地篇：AI 简历诊所怎么一步一步做出来。

关键时间：今天 11.09，报名截止 11.30，初赛材料约 12 月中旬提交。我们只有五周，一切安排都按”五周能交”倒推。

一、我们要做的东西：一页纸讲清产品

产品定位：面向大学生求职的简历修改助手。用户上传简历、粘贴目标岗位 JD，系统给出「多视角修改建议 + 质量评分 + 择优后的最优建议」。

核心闭环（这是整个项目的骨架，五周就围绕它搭）：

创新点（答辩时反复强调这一句）：市面上的 AI 改简历工具都是「单次生成、质量不可控」；我们做的是「生成-评分-择优」闭环——奖励模型用人类偏好数据微调，学到的是”HR/导师眼中的好建议”，相当于给大模型输出加了一道质检关。

为什么奖励模型在这里是刚需而不是噱头：同一个 LLM 对同一份简历生成 3 份建议，质量参差；人工挑不现实，通用 LLM 自己评自己不可信——一个独立训练的小奖励模型既便宜又快，还能给出可量化分数，正好同时满足赛题的「创新性」和「可量化指标」两个评分点。

二、总体架构与工具链

环节 用什么 为什么选它 对应赛题要求
开发工具 华为云码道 CodeArts 代码智能体（必选） AI 写代码补我们的 Web 短板，且是评分点 体现需求理解→代码生成→构建→修复→部署的价值
大模型生成 华为云 MaaS（代金券买 API） 调 DeepSeek/Qwen 等大模型生成候选建议 华为云产品使用
奖励模型 TRL RewardTrainer + Qwen2.5-0.5B/1.5B 小模型 小、便宜、单卡能训、我已有 DPO 复现经验 创新性核心
后端 Python + FastAPI 轻量、上手快（三人都是 C++ 转 Python） —
前端 Gradio（MVP）→ 静态页 + FastAPI（有时间再升级） Gradio 半小时能出可交互页面 可视化 Demo 页面
存储 华为云 RDS(MySQL) + Redis 赛题明确要求关联 RDS、Redis 任务要求硬指标

里程碑 截止 验收标准（没达到就算没过关）

四、每一步怎么干

M0：地基（11.09–11.12，三天）

目标：把所有阻塞项清掉。

  • 我：确认队内分工签字画押（我=奖励模型/指标，A=后端/云，B=前端/材料）；把这篇手册发给队友。
  • 队长：完成官网组队报名 + 学生认证；过审后当天申请华为云代金券（这是唯一不能拖的事）。
  • 队友A：装 CodeArts 代码智能体（免费申请），注册华为云账号，把官方 Skills 一键部署教程从头走一遍。
  • 队友B：装 Python 环境（3.10+），过一遍语法（列表推导、requests、fastapi 最小例子）。
  • 我：复习 TRL RewardTrainer 最小脚本（直接改之前 DPO 复现的工程骨架）。

交付物：报名截图、代金券申请记录、三人各自跑通一个 hello-world（FastAPI 页面 / MaaS 一次调用）。

M1：生成链路（11.13–11.16）

目标：不需要任何训练，先把「简历进、三份候选出」跑通。

  • 简历解析：用 pdfplumber/pypdf 把 PDF 简历转成纯文本（docx 用 python-docx）。解析失败的格式先手动转文本兜底，解析质量不追求完美。
  • 生成候选：MaaS 调大模型，同一个简历+JD，用三个不同视角的 prompt（①内容深度 ②格式规范与量化表达 ③岗位匹配度）各生成一份建议。三视角天然形成”多候选”，产品故事也更完整。
  • 顺手建 GitHub/Gitee 私有仓库，代码从第一天就入库。

交付物：命令行脚本 python pipeline.py --resume a.pdf --jd jd.txt 输出三份建议到三个文件。

过关标准：拿 5 份同学简历实测，三份建议肉眼可见”有差异、都像人话”。

M2：数据 v1（11.14–11.20，与 M1 并行）

目标：凑出奖励模型的两批训练数据。

  • 公开偏好数据（warm-up）：UltraFeedback 二值化版本，下载 5k~10k 条，格式统一成 prompt + chosen + rejected。用途：先跑通训练管线、给模型打底。
  • 领域偏好数据（核心）：这就是我们的差异化来源，流程固定为流水线：
    1. 收集 60~100 份脱敏简历（网上公开模板 + 征得同学同意的脱敏简历）；
    2. 每份简历 + JD 生成 3 份候选（直接用 M1 的管线）；
    3. 三人按同一套打分规则（1~5 分，只看”这条建议对目标岗位有没有用”）打分；
    4. 分数差 ≥2 的两份配对成 chosen/rejected；每天每人 10 对，10 天约 300 对。
  • 打分规则白纸黑字写成文档（答辩”数据集与数据处理”章节直接用）。

交付物：preference_data/ 目录 + 一份《标注规范 v1》。

过关标准：领域数据 ≥200 对；三人打分有分歧的样本（方差大）标记出来，不硬标。

M3：奖励模型（11.21–11.25）

目标：领域奖励模型能打分、能上线。

  • 训练：TRL RewardTrainer，基座 Qwen2.5-0.5B 或 1.5B；先公开数据 1 个 epoch，再领域数据 12 个 epoch；lr ~1e-5、batch 48，单卡几小时量级。先跑课题组服务器，不等代金券。
  • 评估（内部）：留 20% 领域测试集算 accuracy（预测 chosen>rejected 的比例），目标 >60%。
  • 上线：把模型包成打分 API（FastAPI 一个 /score 接口，输入候选建议文本，输出 0~1 分数）。

交付物：训练日志、测试集 accuracy、可 curl 的打分服务。

过关标准：accuracy >60%；/score 接口 100 条批量打分不崩、延迟可接受（<2s/条）。

M4：全链路 + 云上部署（11.24–11.30）

目标：公网可访问的完整 Demo。这是整个五周里最硬的一周，提前一周就开工部署。

  • 集成：Gradio 页面（上传框 + JD 输入框 + 三份建议 + 评分条 + 最优建议高亮）接 FastAPI 后端（生成→打分→择优）。
  • 存储落地：用户记录写 RDS(MySQL)（每次分析存一条），解析结果/候选建议缓存进 Redis（赛题硬性要求 RDS、Redis，务必真实用到、能讲出为什么用）。
  • 部署：官方 Skills 一键部署教程起步 → ECS 上跑起来 → 绑定公网地址 → 手机流量实测能访问。
  • 全链路自测：5 份简历从头跑到尾，截图存档（后面视频和 PPT 的素材）。

交付物：公网 Demo 链接 + 一份《部署复现文档》（readme：依赖、环境变量、启动命令、数据库建表 SQL）。

过关标准：公网可访问、RDS/Redis 有真实读写（截图留证）、全流程无人工干预。

M5：量化指标 + 演示视频（12.01–12.08）

目标：产出初赛材料最值钱的两个数字 + 视频。

  • Spearman 相关性：准备 50100 份简历+JD，每份 3 份候选建议，请导师和同学按 15 分盲评（不知道哪份是谁生成的）；算奖励模型打分与真人平均分的 Spearman 相关系数。目标 ≥0.6。
  • 盲评胜率：同一批样本，”奖励模型选出的最优” vs “随机选一份”，请真人盲评哪份更好，统计胜率。目标 ≥60%。
  • 对照实验（答辩加分项）：奖励模型 vs 直接让强 LLM 当裁判（LLM-as-judge），比相关性——证明”微调过的小模型在简历领域比大模型裁判更准/更便宜”。
  • 演示视频：3~5 分钟，录屏走一遍全流程 + 指标图表 + 我们三个人各讲一段。

交付物：两个核心指标 + 对照实验图表 + 演示视频。

过关标准：数字全部可复现（脚本和数据留档，组委会可能复现）。

M6：材料与提交（12.09–12.13）

目标：把五周的产出打包成初赛材料。

  • 《作品信息收集表》五节对应责任人：背景和价值（B）、创新性解读（我）、数据集与数据处理（我）、关键代码片段解读（我+A）、效果指标（我）。
  • PPT 15 页以内：痛点 → 方案闭环图 → 三视角生成 → 奖励模型训练 → 指标 → Demo 截图 → 分工。
  • 交叉核对：数字、截图、链接逐项对一遍；一切与答辩表述相符（不符会被取消资格）。

五、我的主线任务（奖励模型线）——详解

上面每个里程碑里我的部分，单独拎出来就是一条完整主线：

  1. 数据（M2）：公开数据 warm-up + 领域偏好对 300+。领域对的来源、打分规则、分歧处理全部留文档——这直接变成《信息收集表》的”数据集与数据处理”章节。
  2. 训练（M3）：复用之前 DPO 复现的 TRL 工程骨架，把 DPOTrainer 换成 RewardTrainer，基座换成 Qwen2.5 小模型，训练参数基本照搬。先跑老师服务器。
  3. 指标（M5）：Spearman + 胜率 + 与 LLM-as-judge 的对照。这三个数字是答辩的核心证据，比任何形容词都有说服力。
  4. 叙事（贯穿）：把”为什么奖励模型比大模型直接输出靠谱”讲成一个 30 秒能说完的故事，写进 PPT 创新性页。

时间预算红线：M3 结束（11.25）奖励模型还没跑通，立刻切兜底方案，不再恋战。

六、三个兜底方案（提前想好，翻车不慌）

  1. 奖励模型训不出来 → 打分环节先用「强 LLM 当裁判」（LLM-as-judge）顶上，产品闭环照常跑；奖励模型作为”正在迭代”的部分照写进材料（创新性叙事不变，指标用裁判版的）。先保完整，再求亮点。
  2. 华为云部署连续踩坑 → 官方 Skills 一键部署教程 > 华为云工单/学习空间答疑 > 退而求其次先部署在课题组服务器保证 Demo 可用（材料里仍如实写清部署环境）。
  3. 前端做不出好看页面 → Gradio 就是底线，功能全 > 长得好看；时间富余再换静态页。

七、初赛材料 ↔ 里程碑 映射

初赛要交的材料 由哪个里程碑产出
作品信息收集表（背景/创新性/数据集/代码/指标） M0 定稿框架，M2 数据文档，M4 架构与部署，M5 指标，M6 汇总
PPT / 设计文件 M4 截图素材 + M5 图表 + M6 排版
演示视频 M5
Demo 链接（初赛不强制，但建议给） M4

结尾

五个星期，七个里程碑，一个闭环：简历进去，三份建议出来，奖励模型择优，指标说话。我们唯一要守住的纪律只有两条：一是每周里程碑没过关不往后走，二是所有数字真实可复现。M0 从今天开始。
