任务背景：延续《DPO基线复现报告》，在自己的机器（Dell Precision 7920，RTX 3090×2 各 24GB，驱动 550.135 / CUDA 12.4，root 用户）上跑 DPO / IPO 对照实验。

附 A：显存怎么算（”B 参数” ↔ “GB 显存”）

核心公式：显存(GB) ≈ 参数量(B) × 每参数字节数（fp32=4、bf16=2、int8=1、int4=0.5）。0.6B 全参 DPO 的账：权重 1.2 + 梯度 1.2 + AdamW 状态 7.2（最大头）+ 参考模型 1.2 + 激活 2–4 ≈ 13–15GB < 24GB ✅。

A.1 先看训练的四步流水，显存里的五样东西就对应它

训练时 GPU 里同时住着五样东西，分别对应这四步。

A.2 五样东西分别是什么、为什么占这么多

先把数字拆开：0.6B = 6 亿个数；一份 fp32（4 字节）= 2.4GB，一份 bf16（2 字节）= 1.2GB。下面每一项都是”几份参数大小”的问题。

① 权重 1.2GB——你认识的那堆矩阵数字。模型本体：6 亿个数 × 2 字节。

② 梯度 1.2GB——“每个参数该往哪调多少”的账本。反向传播会给每一个权重算一个导数（∂loss/∂w），梯度和权重一一对应、数量完全一样大，所以又一份 1.2GB。类比：6 亿个学生，每人一张”调参建议单”，单子和学生一样多。

③ AdamW 优化器状态 7.2GB——每个参数三本”高精度账”（最大头的由来）。Adam 更新参数时每个参数要记三样东西，每样都是一个参数对应一个数、且都用 4 字节 fp32：

  • fp32 主副本：bf16 精度不够做微小累加，训练时另存一份全精度权重精确值；
  • m（一阶矩）：梯度历史平均 = 更新方向的”惯性”；
  • v（二阶矩）：梯度平方历史平均 = 每个参数的”自适应步长”。
    三本账 × 2.4GB = 7.2GB——优化器状态是权重的 6 倍（3 份 × 4 字节 vs 1 份 × 2 字节）。

④ 参考模型 1.2GB——DPO 专属的”备份”。DPO 每步都要问”微调前的模型会给这个回答打多少分”，所以原始模型要完整再放一份在显存里（π_ref）。它只做前向、不参与更新，只花权重这一份钱（没有梯度、没有账本）。普通 SFT 训练没有这一项。

⑤ 激活 2–4GB——前向的”草稿纸”。每层前向都给每个 token 产生中间结果（隐藏状态），反向时要回头查它们算梯度，所以必须暂存。它不是参数，随 batch × 序列长度涨缩——UltraFeedback 回答很长，实测总占用 19.6GB 比估算高，多出来的基本都在这一项。gradient_checkpointing=True = “不存草稿、反向时重算”：慢 20–30%，换掉 60–70% 的激活显存。

法则：全参训练 ≈ 每 1B 参数 16GB（权重 2 + 梯度 2 + 优化器 12）；推理 ≈ 每 1B 参数 2GB（只有权重）；LoRA ≈ 每 1B 参数 2–3GB（只有 LoRA 那点参数有梯度与账本）。

附 B：三个坑（上一台实测过）

坑 表现 解决
多卡默认 DDP 不加 --num_processes=1 卡初始化 启动命令必须带（双卡并行也是两个单卡进程，各带各的）
新版 TRL 参数 报 max_prompt_length 未定义 新版删了该参数、不传 tokenizer=（上面的脚本已适配）
用错 Python 装不上新版 torch/TRL 一律 conda activate rl（python 3.10）
eval 阶段 OOM（24GB 卡实测） 训练正常（如 50 步无碍），到 eval 时报 CUDA out of memory DPOConfig 加 per_device_eval_batch_size=1；启动前 export PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True；兜底 eval_strategy="no" 或 max_length 降到 384

附 C：自己的机器，”大胆”的三个选项

  1. 直接上全量数据：两个脚本里 train[:1000] 改成去掉切片（全量约 6 万条），≈7750 步 × 2.5 秒 ≈ 5.4 小时/epoch，对标 Zephyr 的”全量 × 1 epoch”规模，挂着跑即可；
  2. 多种子/多 β：β ∈ {0.05, 0.1, 0.5} 各跑一轮，画”奖励-KL 前沿”迷你版；
  3. 以后新实验：环境 rl 不动，建 ~/rl/simpo/、~/rl/kto/ 等子文件夹，模型继续共用 ~/rl/models/。

附 D：数据量怎么选（推荐三档走）

数据集全量约 6.26 万条 train 偏好对（trl-lib/ultrafeedback_binarized，UltraFeedback 二值化版，Zephyr 同款）。1000 条只是它的 1/62。验证命令：

档 切片 步数 耗时/方法（双卡并行同时出两份） 用途
1 train[:1000] 94 ~4 分钟 流程验证（已完成）
2 train[:10000] 1250 ~52 分钟 中途检查：指标是否稳定上升
3 train（全量） ~7825 ~5.4 小时 最终基线（对标 Zephyr 全量 × 1 epoch）

三个理由：① 1000 条只是”跑通”不是”基线”（accuracy 65.2% 与 BNRM 71.96% 的差距，数据量是头号嫌疑）；② 给老师的对照组必须可信，将来贝叶斯 DPO 要比的就是它；③ 多档数据量正好验证 IPO 论文核心论点——“小样本下 DPO 过拟合、IPO 更稳”：看三档下 DPO 与 IPO 的 accuracy 差距如何变化。

改法与规则：脚本里 split="train[:1000]" 一行改成对应切片，其余不动；DPO 与 IPO 始终同一档、同一超参（唯一变量 = 数据量）；epoch 统一保持 1（全量 1 epoch 是 Zephyr 配方，小档想多练需两方法一致并标注清楚）。

预期看点：accuracy 随数据量上升（朝 BNRM 的 71.96% 靠近或超过）；DPO 的 margin 无天花板、一路涨，IPO 的 margin 收敛到 ——三档数据把两条曲线画在一起，就是”IPO 论文图 1/图 2 在 LM 尺度的复现”，是汇报里最有说服力的一张图。

附 E：DPOConfig 每个超参数详解（我们的脚本逐行版）

想看 DPOConfig 完整参数清单（100+ 个）与默认值，在服务器上跑：

下面按三组逐个讲我们脚本里用到的每一个。

E.1 训练基础组

参数 管什么 我们的值 为什么是这个值 / 怎么调
output_dir checkpoint 和中间结果写到哪个目录 ./dpo_output IPO 版改成 ./ipo_output，两个实验的输出分开
num_train_epochs 整个数据集从头到尾过几遍 1 全量数据 1 epoch 是 Zephyr 标准配方；小档数据（1k/10k）想多练可以加，但 DPO/IPO 必须保持一致
learning_rate 每步更新参数的步长 1e-6 LM 本来就会说话，对齐只是”微”调；太大（>1e-5）会把概率分布搅乱（等价于 KL 约束失效）；DPO 论文原版就是 1e-6
per_device_train_batch_size 单张卡一次前向喂几条样本 1 受显存限制的最小值；越大梯度估计越稳，但吃显存
gradient_accumulation_steps 累积多少步的梯度后再统一更新一次参数 8 有效 batch = 1 × 8 = 8。总步数 ≈ 训练条数 ÷ 8（800 条 → 94 步，你日志里 epoch 0.534 @ step50 就是这么来的）。想贴近 DPO 论文原版 batch=64 就把它调到 64（显存不变，只是更慢）
per_device_eval_batch_size 验证集评估时单卡一次喂几条 1 实测必加：默认值较大，24GB 卡会在 eval 阶段 OOM（你踩过的那个坑）
seed 随机种子（数据切分、初始化等） 42（未写=默认） 做多种子实验时改它（如 0/1/42）看结果方差

E.2 DPO 专属组

beta = 0.1——全文最重要的一个旋钮。管什么：DPO 里 β 是”KL 正则强度 + 隐式奖励缩放”二合一——β 越大，允许偏离参考模型的幅度越大，模型越敢大幅修改概率。IPO 里同一个参数就是论文里的 τ，还额外决定回归目标 （β=0.1 → 目标 5）。怎么调：越小越保守（贴近 π_ref、生成稳但对齐慢），越大越激进（margin 涨得快但有过拟合风险）。论文默认 0.1；想画”奖励-KL 前沿”就扫 {0.05, 0.1, 0.5}。

loss_type = "ipo"——损失函数开关（默认 dpo）。这就是”只换最后一行损失”的那个开关本体。可选值随 TRL 版本增加：dpo / ipo / kto / cpo / orpo / simpo 等。DPO 与 IPO 对照实验里，它是唯一允许不同的参数。

max_length = 512。管什么：prompt + 回答拼起来最多保留多少 token，超长截断。它同时管两件事——模型能看到多长的上下文（内容完整度）和显存（注意力矩阵随长度平方增长）。UltraFeedback 的回答普遍很长，512 是折中；再遇 OOM 优先降到 384。

remove_unused_columns = False。管什么：Trainer 默认（True）会自动删掉数据集里”模型输入用不到”的列；但 DPO 需要 prompt/chosen/rejected 三列原样进入数据整理器（collator），删了就会报 KeyError。必须设 False。

E.3 显存与日志组

bf16 = True。管什么：bfloat16 混合精度训练——权重和激活用 16 位存、算，显存约省一半、速度更快；训练同时保留 fp32 主副本防精度损失（这就是显存账里”优化器 7.2GB”的由来）。3090（Ampere）支持；老卡 V100 不支持就改 fp16=True。

gradient_checkpointing = True。管什么：前向时不保存中间激活、反向时现场重算——用约 20–30% 的训练时间，换掉约 60–70% 的激活显存。0.6B 全参 + 24GB 卡的必备开关。

logging_steps = 5。管什么：每 5 步打印一次指标（loss、rewards/margins、rewards/accuracies、logps/*、entropy、grad_norm 等）。你 dpo.log 里那一行行 JSON 就是它产的。设 5 = 高频观察，适合调试期。

save_strategy / save_steps。管什么：什么时候存 checkpoint。"steps" = 每 save_steps 步存一次（我们每 50 步一次）。训练结束还会单独存一份 ./final（脚本里的 save_model）。

eval_strategy / eval_steps。管什么：什么时候在验证集上评估。"steps" = 每 eval_steps 步跑一轮验证集指标——你第 50 步那次 OOM 就发生在这里（已用 per_device_eval_batch_size=1 修好）。想彻底省事可设 "no"（训练日志里已经有全部指标，eval 只是它们的验证集版本）。

report_to = "none"。管什么：训练指标上报到哪。"none" = 只打印终端；"wandb" / "tensorboard" = 接可视化平台。服务器没配 wandb 就保持 none。

E.4 启动命令行里的三个参数（不在 DPOConfig 里，但同样管训练）

参数 管什么 注意
CUDA_VISIBLE_DEVICES=0/1 让程序只看见指定的卡 0 = 挂桌面的卡、1 = 干净卡；双卡并行时两个终端各设各的
--num_processes=1 accelerate 单进程运行 必须带：多卡工作站默认尝试 DDP 会卡初始化（上一台实测）
--mixed_precision=bf16 accelerate 层精度开关 与脚本里 bf16=True 呼应，两层都开才生效

E.5 你没写但默认值在悄悄生效的常用参数

参数 默认值 管什么
lr_scheduler_type cosine 学习率调度曲线；你日志里 lr 从 9.6e-7 缓慢下降就是它在走
warmup_ratio 0.1 前 10% 步 lr 从 0 线性升到设定值（防开局震荡）
max_grad_norm 1.0 梯度裁剪上限；日志里 grad_norm 200+ 是裁剪前的原始值

max_grad_norm 详解（IPO 实验实测踩过）：梯度裁剪 = 把所有参数的梯度拼成向量 g，若 ‖g‖ 超上限就等比例缩小（方向不变、步长受限），防一步更新过大炸 loss。判断标准：看日志 grad_norm——若常年贴着 max_grad_norm 说明裁剪频繁生效（该放宽或减小损失尺度），远低于则正常。实测教训：IPO（β=0.1）的 grad_norm 达 553–1576，被默认 1.0 裁到每步只剩 1/500–1/1500 → loss 卡 25 不降。修复：beta=0.5 + max_grad_norm=10.0（常见范围 1.0–10.0，别一步关掉，防 NaN）。
| optim | adamw_torch | 优化器；DPO 论文原版用 RMSprop，TRL 默认 AdamW（两者都对） |
| weight_decay | 0 | L2 正则；对齐任务一般不加 |
| save_total_limit | None | 只保留最近 N 个 checkpoint（磁盘紧时设 2） |

E.6 一句话总结：哪些参数动不得

DPO vs IPO 对照实验里，唯一允许不同的参数是 loss_type。 β、lr、batch、epochs、max_length、seed 全部必须两方法一致——否则对照就不是”只比损失函数”了。想扫超参（β、数据量、种子），两边一起扫。
